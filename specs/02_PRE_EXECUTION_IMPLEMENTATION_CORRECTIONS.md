# C1. Primary privacy estimand M(V)

The scientific spec already states that cross-view headline comparisons use common-FPR `TPR@1%FPR`.

Therefore freeze:

\[
\boxed{
M(V)
=
\mathrm{TPR}_{\mathrm{OOF/eval}}(V\mid \mathrm{FPR}=0.01)
}
\]

where the held-out labels are used **only to estimate the evaluation ROC metric**, never to select:

- descendant;
- pooled method;
- attack hyperparameters;
- operational threshold;
- model;
- experimental cell.

This is standard evaluation, not attack calibration.

## Primary vs operational endpoint

Primary:

```text
M_PRIMARY(V) = common-FPR TPR@1%FPR
```

Secondary operational pair:

```text
M_OPERATIONAL_TPR(V)
M_OPERATIONAL_FPR(V)
```

generated by the calibration-only threshold.

`D_L`, `D_R`, `R_priv`, `G_L`, `G_R`, endpoint eligibility, and the headline privacy-recovery analyses use `M_PRIMARY`.

Operational TPR/FPR is always reported beside it.

Do **not** change the primary estimand to calibration-threshold TPR because realised FPR can differ across views; that would make cross-view gaps partly an operating-point difference.

# C2. Tie-safe common-FPR estimator

The current scaffold's individual-record cumulative ROC plus:

```python
max TPR at repeated FPR
```

must not enter production.

Reason:

If equal scalar scores occur in both classes, there is no threshold that includes one member of the tie group but excludes another. Individual-record ordering can therefore create unattainable ROC points.

Production implementation must:

1. construct ROC points at **unique score thresholds**;
2. add all observations sharing an exact score simultaneously;
3. use a deterministic documented convention;
4. expose the estimator as one tested function used by every view/arm.

Recommended implementation:

```text
tie-safe distinct-threshold ROC
drop_intermediate = false
linear interpolation between valid neighbouring ROC points
```

or an independently implemented mathematically equivalent routine.

Do not use an upper-envelope created from arbitrary ordering inside tied scores.

# C4. DRY-G family-wise null calibration

Replace marginal per-statistic null gates with one family-wise max-statistic calibration.

Use the same planted-null clustered design.

## Calibration bank

```text
N_FWER_CALIBRATION = 2_000
fixed master seeds
```

2,000 is preferred because this is CPU-only synthetic work and gives a more stable 95th-percentile max-statistic estimate than 200 trials.

For every calibration trial compute the null-statistic vector:

```text
Spearman rho
operator residual statistic(s)
mean D_L
mean D_R
Delta_CV
```

Standardise each statistic using a scale estimated **only from the calibration bank**.

For two-sided quantities use absolute standardised deviation.

For one-sided `Delta_CV`, use the positive standardised deviation.

Define:

\[
T_{\max}
=
\max_j Z_j.
\]

Freeze:

\[
c_{\mathrm{FWER}}
=
Q_{0.95}(T_{\max}).
\]

A DRY-G validation trial passes the joint null gate iff:

\[
T_{\max}\le c_{\mathrm{FWER}}.
\]

This directly preserves dependence among assertions and controls the per-trial family-wise false-failure probability at approximately 5%.

## Confidence intervals

DRY-G cell-cluster bootstrap CIs remain useful diagnostics and must be reported.

They are **not a second pass/fail criterion**.

Do not combine an FWER-calibrated max-statistic gate with independent CI-includes-zero gates unless that joint procedure is itself calibrated.

## Validation

Run the same three fixed validation trials.

```text
3/3 joint passes -> PASS
2/3 joint passes -> PASS_WITH_INVESTIGATION
<=1/3 -> FAIL
```

Any `PASS_WITH_INVESTIGATION` retains the existing investigation requirement.

Required artifact:

```text
P0_PRE_DRYG_FAMILYWISE_CALIBRATION.json
```

# C7. Cache invalidation must cover the backend

The production cache identity must change whenever executable scoring semantics change.

The cache key must include a deterministic code identity covering at least:

```text
canonical scorer implementation
HF/PEFT backend adapter
token masking/reduction logic
reference-loss implementation
Min-K implementation
tokenizer revision/config
precision
max sequence length
artifact/model hash
record-set hash
```

A manually typed `scorer_version` string alone is insufficient.

Preferred:

```text
SCORING_CODE_HASH = SHA256(relevant source files + resolved scoring config)
```

Then include `SCORING_CODE_HASH` in the content-addressed cache key.

Negative tests:

```text
backend source change -> cache miss
score reducer change  -> cache miss
unchanged code/config -> cache hit + bitwise-identical scalar score table
```
